## 0. 为什么做（对赛题的回答）

卡片承诺"今晚 82 分值得出门"——评委和用户都会问同一句话：**"你们的算法准吗？"** HERMES-02 的置信度回答"这次预报有多大把握"，本任务回答"这套算法在历史上的真实命中率"——两者合起来才是完整的可信度叙事（AI×产品 15% + 用户价值 20% 的硬证据）。低成本重启的依据：Open-Meteo Historical API 免费提供 1940 年至今逐小时历史天气（开源杠杆），成本只剩人工收集真值日期。

## 1. 背景（自包含）

- 评分引擎 `agents_output/02/light_engine.js`：**纯函数、可离线复算**——给任意历史时刻的天气五字段即可算出当时的晚霞评分。这是回测可行的根基。
- 历史天气：Open-Meteo Historical API `archive-api.open-meteo.com/v1/archive`（免费，ERA5 再分析数据），请求方式与现有 forecast API 同构（参照 `agents_output/02/checks/backtest_c6.mjs:8-10` 的字段与采样法：日落 ±90min 逐小时均值）。
- **已知风险**：ERA5 再分析里 `visibility` 可能缺失或质量差——若缺，走引擎既有的空值缺省路径（`light_engine.js` 用 `??` 缺省），并在报告显著注明"能见度因子按缺省处理"及其对结论的影响。
- 真值从哪来：深圳晚霞在社媒有强打卡文化——小红书/微博搜"深圳晚霞"+翻日期、"深圳 火烧云"；莉景天气公众号的历史预警推文也可作旁证。

## 2. 目标

**A.（人：H2）真值日期集** `agents_output/02/burst_days.v1.json`：
- **爆发日 ≥15 个** + **哑火日 ≥10 个**（哑火=对照组，只收爆发日算不出误报率——那种"看起来会有但最后没有"的普通阴天/晴天日子）
- 时间范围建议近 18 个月（数据新鲜、社媒可查）；schema 给死：

```json
{ "days": [ {
  "date": "2026-05-12",
  "label": "burst | dud",
  "intensity": "大爆 | 小爆 | 无",
  "evidence_url": "https://…（帖子/截图链接，必填）",
  "evidence_note": "≤30字：谁发的/画面什么样",
  "confidence": "H | M | L"
} ] }
```

**B.（AI）回测脚本与报告**：
- `backtest_history.mjs`：读 burst_days → 逐日拉 Historical API 日落 ±90min 五字段 → 喂 `light_engine.score()` → 输出逐日评分明细。
- 报告 `hermes08_backtest_report.md` 必含四件：①爆发日 vs 哑火日的评分分布（中位数/四分位，区分度一目了然）②以现有产品阈值（评分 ≥60 视为"值得出门"）的命中率/误报率/混淆矩阵，阈值作为调参口可敏感性分析（55/60/65 三档）③逐日明细表（日期/真值/评分/五因子贡献——错判日逐个点评为什么错）④**给 AGENT_08 的一句话**（如"近 18 个月 N 个真实爆发日中算法命中 M 个"，只许写真实数字）。

**不做什么**：不改评分公式/权重/阈值定义（错判分析只做归因，调整建议单独列出交决策者）；不做机器学习拟合；不扩展到深圳以外。

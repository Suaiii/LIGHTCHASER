## 0. 为什么做（对赛题的回答）

产品的核心承诺是"告诉你**哪里**有光、值不值得去"。当前 3D 地图有太阳方位光照与建筑受光面，但用户（决策者）判定"告诉他哪里有光，这一点我们做得还不够"——刷到卡片的人 3 秒内应该看懂"光在哪、往哪走"，这直接就是体验完整性（30%）的"刷到即用、无学习成本"。

## 1. 背景（自包含）

- 现状：`public/light-map-gl.jsx` = MapLibre GL + Three.js 共享 WebGL 上下文。已有：真实太阳方位/高度角驱动的平行光、建筑受光/背光面、楼间地面投影、半透明楼群、zoom 驱动生长动画、金色路线（画面最亮元素）、SunCalc 时刻推算控制量。
- 该文件**工程雷区密布**——动手前必读 `docs/3d光影地图-交接文档.md` 第五节"防退化机制清单"（六类共享上下文坑 + 性能红线），已修好的抖动/乱码/消失问题在那里面，破坏任何一条直接打回。
- 决策者已拍板的方向偏好：**光域高亮层**（地面上直接渲染"此刻看得到晚霞的开阔区域"）最贴近直觉；但明确要求**提案制**："要实际演示才能搞清楚"。

## 2. 目标（提案制——本任务书只定验收标准，不定实现方案）

产出 **2–3 个可切换的方案 demo**（Tweaks 面板加开关或 URL 参数切换），候选方向（可组合、可另创）：
- A. **光域地面高亮**：视线不被楼群遮挡、能看到日落方向天空的开阔地带，地面染淡金色渐变
- B. **机位光位标注**：每个机位信标实时显示光位分/最佳朝向小箭头
- C. **太阳轴线**：太阳方位射线 + 观看朝向指示

每个方案附一段自评（对照 §3 验收标准逐条打分）+ 截图/录屏。**决策者实际演示后拍板一个**，落选方案代码删除不留尸体。

**不做什么**：不做随行走旋转（DeviceOrientation，backlog #12）；~~不做附近的人社交光点扩展~~ → **7.15 边界改写**：社区照片气泡层由 **HERMES-10** 承担，本任务仍不实现它，但提案自评需含一段"与照片气泡层共存"的口径（方案 B 机位标注与气泡同为"每机位一点"，空间上如何避让/合并，一段话即可）。

> **⚠️ 7.15 增补（三板块整合联动，全案 `docs/hermes/product-arch-v3.md`）**：①"不喧宾夺主"红线从两层升三层——负责人拍板 D-c 前按建议档执行：**金色路线 > 见光点 > 照片气泡**，取色器验收法不变、对照物加一层；②3 秒测试口径：测试画面**不开**气泡层（气泡未实现，且测的是"哪里有光"单一心智）；③负责人三选一拍板时会连同气泡共存一起考虑（PR #30 已具备 axis/spots/both，等演示）。

## 3. DoD（验收标准，二元——同时是方案设计约束）

- [ ] **3 秒测试**：无说明的情况下，首次看到画面的人能在 3 秒内答出"往哪个方向走能看到光"（找 1 位没参与开发的人实测，记录进提案文档）。
- [ ] **不喧宾夺主**（决策者原话）：新增视觉元素的亮度/饱和度不得压过路线金线——验收方式：截图中路线金线仍是除 HUD 外最高对比度元素（用取色器抽 5 点对比，数据进提案）。
- [ ] **数据真实**：光域/光位计算必须来自真实太阳几何（SunCalc）+ 真实建筑数据（当前视口瓦片），任何"看起来像"的手绘遮罩=直接打回；计算方法写进提案文档可复算。
- [ ] 时刻控制量联动：Tweaks 切换光照时刻（now/17:30/18:50 等）时，光域/标注随太阳方位实时变化。
- [ ] 性能：开启新层后 `scripts/e2e/tower-steps.mjs` 步进测试峰/均 <2.5x 且无新增 JS 错误；`rotation-invariance.mjs` diff 仍 <0.2%。
- [ ] 防退化：交接文档第五节六条机制逐条自查表（附在提案末尾）。

## 0. 为什么做（对赛题的回答）

决策者原话拆解："如果每次都要导航 6-7 公里，我肯定不愿意去"——行动成本必须"恰到好处"，解法之一就是**密度**：任何位置刷到卡片，附近 15 分钟内总有一个"出片点"。而"出片"的本质是**记录美好生活**——不止晚霞：刷到附近的餐馆可以直接导航，刷到美术馆一样可以引导。这是本项目从"晚霞工具"长成"附近的美好瞬间引擎"的潜力所在（场景洞察 20% + 延展潜力 15% 双维度弹药）。

## 1. 背景（自包含）

- 现有机位库 `agents_output/01/spots.v1.json`：25 个深圳机位，scene 枚举**锁定四类** `{sunset:14, skyline:4, exhibition:5, cafe:2}`，每条含坐标/朝向/best_window/构图模板/walk_steps/文案槽等，逐点人工核验（OSM 反查 25/25），有 Node+Python 双校验器。
- 现有评分 `agents_output/02/light_engine.js`：五因子（云/湿度/能见度/日落窗口/天气码）——**只对 sunset 类场景有意义**。餐馆/美术馆的"值不值得现在去"需要另一套因子。
- 治理红线：评分维度改动只走"调参口"，不随意加维度——所以泛化评分是**新的并列引擎设计**，不是往晚霞引擎里塞因子。
- 数据来源现状：①外联（AGENT_07 模板已发）会回流**带真实位置的照片授权**——人工位置，质量高，随到随入库；②OSM POI（Overpass 工具链已在 `scripts/fetch-shenzhen-buildings.mjs` 验证过多镜像轮换+断点续传的打法，可复用）——量大，轻核验；③可颂攻略采集（工具链✅，等首批链接）。
- 决策者拍板：**可以简单入库（轻核验），但不急**；筛选算法要同步扩展设计。

## 2. 目标

**A.（人，随时）外联回流位置入库通道**：外联拿到授权照片时，其拍摄位置按现有 spots schema 建条目：`scene` 暂用现有四类最近似值、坐标标注来源与置信度（`待核`/`外联者提供`）、三件套字段按授权台账规则填。跑双校验器 0 error 才算入库。

**B.（设计稿）schema v2 草案** `agents_output/01/schema_v2_draft.md`：
- scene 枚举扩展提案：新增哪些类（候选：`restaurant / gallery / night / street / park`……由深圳实际出片供给决定，给出每类 ≥3 个真实例证地点）
- 新增字段提案：`photo_index_factors`（该点的出片因子引用）、`source`（人工核验/外联/POI/可颂）、`confidence`（H/M/L）、`open_hours`（餐馆/美术馆有营业时间——晚霞没有的新约束）
- **向后兼容**：v1 的 25 条不改一字仍通过 v2 校验器（校验器扩展方案一并写）

**C.（设计稿）"出片指数"泛化筛选框架** `agents_output/02/photo_index_draft.md`：
- 问题定义：任意 scene 类型的点，"此刻值不值得去拍"= f(光照条件, 场景属性, 时段匹配, 行动成本)
- 分层设计提案：**通用层**（步行距离/开放状态/时段窗口）× **场景层**（sunset→现有五因子引擎原样复用；restaurant→光线时段+室内外；gallery→展期+人流……）
- 明确治理：每个场景层的因子与权重独立声明、独立调参口，晚霞五因子引擎**零改动**
- 边界态：新场景的"劝退"文案逻辑（对齐 AGENT_05 的边界四态设计）

**不做什么**：不实现代码；不批量抓 POI（押后）；不动 spots.v1.json 已有 25 条；不做全国扩展（深圳内做深）。

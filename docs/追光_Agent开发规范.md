## 1. 当前项目准口径

追·光**不是**一个由我们直接写产品代码的项目：最终产品在**抖音AI平台**（`douyin-ai.bytedance.net`）由人以 vibecoding 方式搭建，我们产出的是"让平台 AI 写对代码的话"（规格 / 数据 / 提示词）。因此本仓库的一切文档只有两类：**指导弹药生产的真理源**，与**追溯性背景**。

开发时必须按以下优先级读取当前文档：

1. `docs/赛道细则/instruction.md`（正文为 `docs/赛道细则/image/instruction/*.png` 截图 ×11）：赛道三官方细则——最高外部约束，评审维度、平台要求、提交要求以此为准。
2. `Thoughts/AGENT_00_总控.md`：**编队宪法**（第一性原理 F1–F6、共享上下文胶囊、编队一览与依赖图、关键日历、运行规则、Gate 0/1/2 二元判定）。任何 agent 开工前先读其 §1/§2。
3. `Thoughts/追光_总设计蓝图_v2.md`：**作战蓝图**（五个 Part、P0–P3 阶段地图、初赛资产→平台机制映射表、跨 Part 接口契约、风险登记册、立即行动清单、四条设计原则）。编写日期 7.11，**取代 v1 计划中与本文冲突的内容**。
4. `Thoughts/AGENT_01_机位库.md` … `Thoughts/AGENT_08_叙事展陈.md`：各 agent 的任务卡/规格（§1 第一性原理 … §9 升级条件的九段结构），是每个开发切片的直接依据。
5. `docs/立意/思路.md` / `docs/立意/中文故事.md`：产品立意、商业分析与叙事文案（初赛沉淀），供理解"为什么"。
6. `CLAUDE.md`：工程约定——技术栈与版本、编码规范、项目结构、怎么跑/怎么测、提交前检查清单、当前状态与遗留问题。
7. `agents_output/`：已交付物与各自 `checks/check_report_XX.md` 检查报告（当前已含 `01/` 机位库、`02/` 光线引擎）。
8. `DEVLOG.md`：dated 开发流水，历史决策与问题（新条目置顶）。

**源头真理（冲突时以此为准）**：`Thoughts/AGENT_00_总控.md` + `Thoughts/追光_总设计蓝图_v2.md`。外部规则以 `instruction.md` 为准；两者与内部文档冲突时，规则 > 宪法/蓝图 > 其余。

**仅追溯查看（已被取代，不得据此开工）**：

prototype/docs/*                     # 初赛交流赛的交接/路演/部署文档，Vite+Vercel 路线已作废

## 2. 第一性开发原则

以下原则合并自 AGENT_00 的六条第一性事实（F1–F6）、v2 蓝图的四条设计原则、以及 CLAUDE.md 的工程红线。每一条都可执行、可据以否决。

**A. 编队第一性事实（F1–F6，一切任务由此推导）**

1. **前 5 秒定生死（F1）**：评审锚点是"用户刷到的一瞬间是否被打动、被满足、并自然产生一次互动"，体验完整性占 30%（全场最高权重）。→ 一切设计以刷到后前 5 秒的信息效率为最高优先级；任何挡在前 5 秒里的东西都砍。
2. **我们写"让 AI 写对代码的话"（F2）**：作品必须经抖音AI平台以 vibecoding 产出（feed 卡 + 小程序）。→ 规格、数据、提示词的质量 = 产品质量；本编队的产出物就是这些"话"。React 代码库是弹药不是最终交付物。
3. **评委即用户，深圳即现场（F3）**：评委在深圳、比赛当天下午亲手扫码体验。→ 数据的"此刻真实性"（当天深圳的真评分、真日落）是最强说服力；任何写死的假数据都是自我降级。
4. **平台 7.24 才开门，现场只有 40 小时（F4）**：→ 一切可离线预制的（太阳数据、机位库、文案样例、规格、话术）必须在 7.24 前预制完毕；平台期只做"翻译与还原"，现场期只做"整合与发布"。
5. **开发人力稀缺，决策带宽是瓶颈（F5）**：→ 每个任务写成 agent 文件、交付条件二元化（打勾即验收，不需思考），人只做机器做不了的事：拍板、外联、现场执行、验收。
6. **素材合规一票否决（F6）**：章程严禁未授权素材。→ 每一张图有可追溯的权利链（授权凭证或自拍记录），宁缺毋滥。

**B. 由评审表反推的四条设计原则（所有 Part 取舍以此为准绳）**

7. **前 5 秒原则**（体验完整性 30%）：0.5 秒评分可读，1.5 秒看懂"今晚值不值得"，3 秒内产生第一次互动欲望。
8. **AI 可见原则**（AI 能力 15%）：AI 不是后台黑盒——评分、行动文案、拍摄建议要让评委"看见 AI 正在为此刻的我判断"；平台的 Skill/知识库/豆包模型机制要显性用上。
9. **此刻原则**（场景洞察 20% + 用户价值 20%）：所有内容锚定"现在、这里"——评委在深圳、当天下午刷到，卡片说的就是当天傍晚的深圳。
10. **再刷到原则**（延展潜力 15%）：卡片自带"明天预告"与随时间变化的状态，让人期待下一次遇见。

**C. 工程红线（不可逾越，违反即 Blocking，见 §14）**

11. **不编造数据/地点**：无把握写保守版并标 `待核` + 置信度；不得凭空生成坐标、时刻、评分。
12. **不搬他人样张/文案**：`sample_img / sample_credit / consent_ref` 三件套同空或同非空；非空时 `consent_ref` 必须指向 `AGENT_07` 授权台账行号；文案表述一律重写，不粘贴他人笔记原文。
13. **评分因子锁 5 个，不加维度**：评分公式 v2 锁定云分层 / 湿度 / 能见度 / 时窗 / 天气码；改动只在指定"调参口"，可解释优先于拟合。
14. **每份交付物必附检查报告**：`checks/check_report_XX.md`，DoD 逐条二元、K 检查任务带真实证据（脚本输出 / 截图 / 链接）；**无检查报告 = 未交付**。
15. **不静默截断或丢失信息**：数据、模型输出、错误、证据不得用 `[:N]`、substring、隐式摘要方式截断；遇边界应保留原始真相并显式派生摘要，或以明确错误拒绝写入。
16. **凡无必要，勿增实体**：新增字段、表、枚举、页面、组件前先证明现有结构承载不了（例：`AGENT_01` K4 对"样张参考流"选择复用单样张聚合而非过早增 `sample_gallery[]`）。

## 3. 标准开发管线

每个开发切片（一个 agent 任务 / 一张 Part 任务卡）必须走这条主线：

```text
赛题 / 需求澄清
  -> agent 任务卡 / 规格（AGENT_XX §1–§9  或  PART 任务卡：使命/Owner/接口/DoD）
  -> 可离线预制的弹药产出（入 agents_output/<编号>/）
  -> 自检 + 检查报告（DoD 二元 + K 检查任务带证据）
  -> 人验收（H1/H2 对照 DoD 打勾）
  -> Gate 判定（Gate 0 / 1 / 2 的二元一票否决）
  -> DEVLOG.md 追加一条 dated 流水
```

关键约束：

- **最终产品在抖音AI平台由人 vibecoding 搭建，我们产的是让平台 AI 写对代码的话**。因此"实现"不是写产品代码，而是把弹药做到"即插即用、平台 AI 拿到即能还原"。
- 一切可离线预制的弹药必须在 **7.24 平台开放前**做完（F4）；平台期只做翻译与还原，现场期只做整合与发布。
- 除极小的文案 / 路径修正外，不跳过"任务卡 → 检查报告"这一步；口头"做完了"不算数（§13）。

## 4. 角色分工

追·光用**五个 Part**（任务域，非人头）组织工作，Part 之上叠加 **AI 与人的二元分工**（AI 主导产弹药，人负责机器做不了的事）。

**主表：五个 Part（源自 v2 §3）**

| Part | 使命（一句话） | Owner | 主要接口 |
|---|---|---|---|
| PART-P 平台工程 | 在抖音AI平台产出真实入 feed 的卡片+小程序，还原原型体验 | A | 消费 X 的规格、D 的数据、C 的素材 |
| PART-D 数据与光线引擎 | 评分公式、机位库、太阳/天气数据链路、豆包文案能力 | B | 向 P 供数据表/Skill/提示词 |
| PART-C 内容与授权 | 合法样张与步导素材（授权为主、实拍为辅）+ 用户访谈 | C（授权外联由提出该策略的成员主抓） | 向 P/N 供图，向 N 供语录 |
| PART-X 体验与动效规格 | React 原型 → Figma 稿 → 平台还原度守门 | A/C 共担，A 拍板 | 向 P 供 Figma+tokens+首5秒规范 |
| PART-N 叙事与展陈 | 海报、游园会展位、话术、（自选）说明材料 | C 牵头，全员供弹 | 消费所有 Part 的成果 |

**AI 与人的分工（源自 AGENT_00 §3/§5）**

- **AI 主导产弹药**：机位库、光线引擎、文案样例、需求包、外联工具件、叙事文稿等的起草与自检（见编队一览的"执行者"列，多为"AI 主导，HX 验收"）。
- **人负责机器做不了的事**：拍板、外联发送、现场执行、验收。两人分工：**H1 = 工程线**（04 共建、05 评审、06 执行、7.25 起平台搭建主驾）；**H2 = 数据内容线**（01/02/03/07 的 agent 调度与验收、08 定稿、平台期副驾 + 数据导入）。Gate 会议、7.28 实拍、游园会展位两人共同。

**对应 `agent.md` 四角色的映射**

| agent.md 角色 | 追·光对应 | 职责 |
|---|---|---|
| Codex 主会话 | 总设计师 / H1·H2（拍板） | 赛题澄清、规格收敛、Gate 裁决、验收、编队调度 |
| Research / Explorer 子任务 | 调研子代理 | 查平台能力、查坐标真值、对比方案，输出证据与简明结论，不做产品终判 |
| Implementation 会话 | agent 执行者（AI 主导） | 按 AGENT_XX 任务卡产范围内弹药、自检、附检查报告、汇报 diff |
| Review 会话 | 验收与检查报告审查 | 审 DoD 与 K 证据、找红线违反、severity 分级，不替代人验收 |

> **人数口径（2026-07-12 用户确认）**：团队为 **2 人（H1/H2）**，以 `AGENT_00 §3` 为准（原三人 A/B/C 分工作废）。五 Part 保留为任务域组织方式（一人多戴帽）：Part 表中的 Owner A/B/C 映射到 H1（工程线：P/X 拍板）与 H2（数据内容线：D/C/N 验收）。

## 5. 需求澄清规范

赛题 / 命题不清时先澄清，不急着产弹药。

**必须搞清楚：**

- 该切片解决的真实用户问题是什么，对应评审哪一维（场景洞察 20 / AI×产品 15 / 体验完整性 30 / 用户价值 20 / 延展 15）。
- 影响哪个 Part（P/D/C/X/N），是否跨 Part（跨 Part 需对齐 v2 §8 接口契约）。
- 是否改动共享口径：四页结构、视觉 tokens、评分等级（≥75 值得跑出门 / 45–74 顺路看看 / <45 今天歇着）、评分因子（锁 5 个）。
- 是否改动数据 schema（`spots` / `sun_events` / `weather_daily` / `copy_samples`）——改动即波及下游多个 agent。
- 是否依赖 7.24 后才能测定的平台能力（动效自由度 / 定位 / 外部 API / 审核时长）——若依赖，先记为 `⚠️` 占位并挂进 `AGENT_06` 十二问。

**三个悬置确认项（v2 §10，未确认前按保守口径开工并标注）：**

1. **D1 具体日期**：章程口径 7.31，思路口径 7.28（若 D1=7.31，则 7.28–7.30 为深圳整备期，与 7.28 抵深实拍吻合）。
2. **除海报与作品链接外，是否还有其他提交材料**（说明文档 / 视频是否需要）。
3. **选手互评是否计入奖项**。

**澄清产物放哪：**

- 涉及编队级口径或跨 Part → 写入 `Thoughts/`（并在 `DEVLOG.md` 记一条）。
- 单 agent 内的澄清与问题清单 → `agents_output/<编号>/`（如 `AGENT_05` 的 `open_questions.md`、`AGENT_06` 的十二问）。

## 6. 规格 / 任务卡草案规范（对应 PRD / Contract）

追·光的"PRD / Contract"有两种形态：**AGENT_XX 规格文件**（九段结构）或 **PART 任务卡**。

**形态一：AGENT_XX 规格（九段，是每个数据/内容/需求切片的机器真相源）**

```text
§1 第一性原理        —— 该任务为何存在，锚定哪条 F / 哪个评审维度
§2 上下文胶囊        —— 自带上下文，执行者无需读其他文件即可开工
§3 目标（Goal）      —— 一句话可验收的产出目标
§4 输入              —— 上游依赖与素材来源
§5 交付物            —— 逐个文件 + schema/字段定义
§6 交付条件（DoD）   —— 逐条二元判定（C1、C2…）
§7 检查任务          —— 交付前逐条执行、带证据（K1、K2…）
§8 禁区与红线        —— 该任务专属的不可逾越项
§9 升级条件          —— 触发即停手问人的信号
```

**形态二：PART 任务卡（v2 §4，用于阶段级任务分派）**

```text
使命（一句话） / Owner（对 DoD 负责的唯一人） / 主要接口（供谁、需谁）
任务（分条） / 验收（DoD，可二元判定）
```

对"接口 / 字段 / schema"类需求，优先写规格（含字段定义与枚举），而非长叙述——跨 Part 交付以 v2 §8 接口契约表的"格式与标准"为准。

## 7. 切片（Issue）规范

每个切片必须是**可独立产出、可独立验收的垂直弹药**，不按"数据一个切片、文案一个切片"机械切，而按 agent 任务 / 交付物切。

切片字段：

```text
任务（Title）
执行者              # AI 主导 · 人验收 / 人机结对 / 人主导，标明 H1 或 H2 验收
时间窗              # 对齐 AGENT_00 §4 日历与 v2 阶段地图
上游依赖            # 例：AGENT_03 依赖 AGENT_01/02
下游                # 谁消费本产出（下游 agent / 平台表）
交付物              # 逐个文件 + schema
交付条件（DoD）     # C1、C2… 逐条二元
检查任务            # K1、K2… 带证据
禁区与红线
升级条件            # 触发即停手问人
状态：ready-for-agent | needs-more-spec | in-progress | ready-for-review | done
```

位置约定：

```text
Thoughts/AGENT_XX_<名>.md        # 切片规格（任务卡）
agents_output/<编号>/            # 切片产出物（数据/脚本/文档）
agents_output/<编号>/checks/     # 检查报告与证据
```

参照已交付的 `agents_output/01/`（机位库）、`agents_output/02/`（光线引擎）目录形态。

## 8. 交付门（Routing Gate）

**切片级门（进入产弹药前，主会话必须回答）：**

1. 是否有明确的 DoD（每条能二元判定）？
2. 是否可离线预制（不依赖 7.24 后才能测定的平台能力）？依赖则记 `⚠️` 并挂 `AGENT_06` 十二问。
3. 上游是否就绪（依赖的 agent 已交付且检查报告闭环）？
4. 若失败如何降级（是否已预置降级形态，如 `AGENT_04` 的悬浮窗/罗盘降级方案、`AGENT_07` 的授权 15→10 降级）？
5. 范围是否足够小、能交给一个 agent 会话独立完成？

结果只有两种：

```text
ready-for-agent      # 可执行
needs-more-spec      # 需补规格（不得进入产弹药）
```

**编队级门（Gate 0/1/2，二元一票否决，源自 AGENT_00 §6 / v2 §4–§6）：**

- **Gate 0（7.23 晚）**：`AGENT_01/02/03/04/05` 全部 DoD 打满勾 + `AGENT_07` 达成 ≥15 机位授权或已启动降级预案。通过后 P1 平台冲刺期开闸。
- **Gate 1（7.27 晚）**：真实抖音 App 扫码 → 封面/轻导航/攻略/快拍四页 60 秒内走完零报错，卡片的评分/文案/机位**来自数据库与模型而非写死**；`AGENT_06` 十二问全部有据。**不通过 → 7.28 白天为唯一补救窗口，PART-N 工作全部让路。**
- **Gate 2（7.30 晚）**：队外一人无讲解盲测，能在 **5 秒内**说出"这卡在让我干什么"、60 秒内完成一次完整互动；素材权利链 100% 可追溯。

## 9. 实现规范（产弹药规范）

执行者（AI 主导）必须：

## 11. 后端开发规范

追·光没有传统后端——"后端"是**数据与算法资产**，须映射到抖音AI平台的机制（v2 §3 映射表）：

| 初赛资产 | 平台机制 | 落点 |
|---|---|---|
| 评分公式 / 光线引擎（`light_engine.js`、`score_spec.md`） | 自定义 **Skill** 或 **工具** | 卡片实时评分与"AI 可见" |
| 机位库 JSON（`spots.v1.json`） | **数据库表**（附件上传导入） | 攻略页数据源 |
| 精修文案库 + LLM 调用（`copy_samples`、`prompt_pack`） | **生成式模型**（@Doubao-seed-2.1-pro）+ few-shot | 行动文案 / 拍摄建议 |
| 摄影方法论 / 步导知识 | **知识库** | AI 回答的专业性 |
| React 动效与视觉 | **Figma 导入** + 对话调优 + frontend-design skill | 还原度 |
| 真实用户数据需求 | **扫码授权**（抖音账号）/ 抖音数据 API | 个性化与真实性 |

数据 / 算法交付硬规则（CLAUDE.md §3 + AGENT_01/02）：

- **可离线、可复算**：评分与几何类用纯函数，不依赖运行时外部状态；太阳数据用 SunCalc（`^1.9.0`）离线预计算（当前 `sun_events.v1.json` 覆盖 25 机位 × 18 天，7.31 日落 19:07）。
- **字段 `snake_case`**：`spot_id`、`cloud_low`、`best_window`、`azimuth_10min`。
- **id 前缀规范**：`场景前缀-三位序号`，前缀 `szw`（晚霞/滨海）`szs`（天际线）`sze`（展览）`szc`（咖啡），如 `szw-001`。
- **枚举锁定**：`scene ∈ {sunset, skyline, exhibition, cafe}`；`compose_template ∈ {thirds, leading, silhouette, frame}`。
- **评分因子锁 5 个**：云分层 / 湿度 / 能见度 / 时窗 / 天气码，改动只在指定调参口，不加维度。
- **坐标经反查核验**：新增/改动机位过 `agents_output/01/checks/geo_verify.mjs`（OSM Nominatim 反查，落正确深圳区县；核验中曾纠正 `szw-012` 一处跨境错误）。
- **文案约束**：`copy_slots.hook ≤26 字`，`tip1/2/3 ≤15 字`。
- **天气双预案**（`weather_ops.md`）：在线 API 版 / 每日人工刷新版，A/B 选型待 `AGENT_06` 7.24 平台测绘定夺。
- **数据一致性**：`01 ↔ 02` 的 `spot_id` 集合必须完全一致（生成器直接消费 `spots.v1.json` 的 id，构造保证 + 运行时 diff 复核 `idMatch=true`）。

本机工具链（CLAUDE.md §1）：Node.js `v24.14.1`（含 global `fetch`）；Python anaconda `3.12.7` @ `E:\anaconda\python.exe`（跑 `.py` 用全路径 + `PYTHONUTF8=1`，⚠️ 系统 `py` / Store `python` 已损坏勿用）；坐标核验走 OSM Nominatim（限速 1.1s/请求）。

## 14. Code Review 规范

Review 审查的是**检查报告与交付物**，findings 前置，先列风险。

严重级别：

1. **Blocking**：编造数据 / 搬运未授权图 / 静默截断或不可逆信息丢失 / 未验收产物进主线。
2. **High**：破坏产品模型（三板块结构——7.15 起以 `docs/hermes/product-arch-v3.md` 为准、评分等级、tokens 口径）/ 过度实现 / 新增无必要实体（字段、表、页面、枚举）。
3. **Medium**：违反任务卡规格 / 缺边界态（低分/雨天/夜间/无样张）/ 缺检查任务或证据。
4. **Low**：命名、文案、局部清理。

必查项（对应追·光红线）：

- 是否编造坐标/时刻/评分？无 `待核` 标注的臆造 → Blocking。
- 样张三件套是否满足同空/同非空、`consent_ref` 是否指向台账行号？违反 → Blocking。
- 评分是否新增第 6 个因子 / 改动可解释口径？→ High。
- 是否有静默截断、隐式摘要、`[:N]`？→ Blocking。
- DoD 是否逐条二元、K 任务是否带真实证据？缺证据 / 只写"通过" → Medium/High。
- 数据一致性（`01 ↔ 02` `spot_id`）是否复核？未核 → High。
- 文案是否 `hook ≤26` / `tip ≤15`、是否有幻觉（引用不存在的机位/时间）？违反 → High。
- 是否新增无法证明必要性的字段/页面/组件？→ High。

Review 不写泛泛总结，不替代人验收。

## 根因判断

demo 服务器虽然接受 `/foot/` 路径，五条响应的时长却只相当于每公里 1.13–3.45 分钟。这个速度不可能来自步行 profile，并且与同坐标的 routed-foot 结果相差约 4–12 倍。根因可以确定为：旧链路把 OSRM demo 的机动车数据集当成步行数据使用。坐标经纬度顺序没有问题；真正出错的是服务端 profile。

前四条路线起步后到终点的直线距离立即下降，没有机动车单行道式反向绕行。第五条的前约 185 米先沿海上世界广场的已映射步道向北，随后转向南；FOSSGIS 与 Valhalla 给出相同路径，说明这是 OSM 步行路网的接入结果。该路线末点还会吸附在距机位约 369 米的可达路网上，因此不能把它写成“全程单调朝终点”。P3 必须继续展示 `walk_steps`，7.28 实拍时应核对广场内部穿行口并补最后一段步导。

## 实现与降级验证

- `lib/route-service.js` 改用 FOSSGIS routed-foot，返回字段仍是 `source/distanceMeters/durationSeconds/geometry`。
- 每次响应计算 `duration / distance`；超出每公里 10–16 分钟时抛出 `osrm_untrusted_walking_pace`，沿用原有 8 秒超时、2 次重试和直线兜底。
- `scripts/test-sunset.js` 注入 1 分钟/公里的伪成功响应，验证 3 次尝试后返回 `fallback-straight-line`。
- 同一测试注入 HTTP 500，验证 3 次尝试后返回 `fallback-straight-line`，`fallbackReason=osrm_failed:500`。
- `npm run test:api` 会请求真实 routed-foot，并断言金山路线的步行速度落在每公里 10–16 分钟。

## 结论与限制

替换后，五条路线的时间都符合步行速度，距离与 Valhalla 交叉结果一致。代码还能识别未来服务误配为 car profile 的情况，不会再把机动车时长显示成步行承诺。尚未闭环的是海上世界广场内部 369 米的路网缺口；这需要现场步导补齐，公共 OSM 路由本身不能提供可靠的园区内最后一段。
